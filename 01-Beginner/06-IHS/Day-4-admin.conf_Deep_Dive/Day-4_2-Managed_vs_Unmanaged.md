# IBM HTTP Server (IHS) with WebSphere — Managed vs Unmanaged

A beginner-friendly guide explaining how IBM HTTP Server integrates with WebSphere Application Server (WAS), and the difference between **Managed** and **Unmanaged** web server configurations.

---

## 1. The Big Picture

Imagine a bank's website:

- Customers hit a **web server** (the "front door").
- The web server doesn't do the real work. It forwards requests to **WebSphere Application Server (WAS)**, where the actual banking application runs.

The web server here is **IBM HTTP Server (IHS)**.

### The Problem

IHS needs to know **which WAS servers to forward requests to**, and **which apps live on them**. This information is written in a file called:

```
plugin-cfg.xml
```

> [!NOTE]
> `plugin-cfg.xml` is the **"routing instruction file"**. It is generated by WAS (DMGR). IHS just needs a copy of it.

---

## 2. What is DMGR?

**DMGR = Deployment Manager** — the "boss" server.

- It is the **central brain** of the WebSphere cell.
- You control everything from its console (default admin port: `9043`).
- It knows all your app servers, clusters, and web servers.

Whenever your application changes (new app deployed, cluster changed), **DMGR regenerates `plugin-cfg.xml`**.

Then the question becomes:

> **How does this file get to IHS?**

That is where **Managed vs Unmanaged** comes in.

---

## 3. What is the IHS Admin Server?

IHS is basically an Apache web server, but it also has an **optional helper process**:

### IHS Admin Server

- Runs on port **`8008`**
- Its **only job**: accept commands from DMGR, such as:
  - "Here's a new `plugin-cfg.xml` — copy it."
  - "Restart yourself."
  - "Start / Stop IHS."

It is protected by a **username + password**:

```bash
htpasswd -c /opt/IBM/HTTPServer/conf/admin.passwd ihsadmin
```

| Parameter | Meaning |
|---|---|
| `htpasswd` | Creates the password file |
| `-c` | Create a **new** file |
| `ihsadmin` | The username |
| `admin.passwd` | Stores a **hashed** password (not plain text) |

The file `admin.conf` tells the Admin Server to use this password file:

```apache
AuthType Basic
AuthUserFile /opt/IBM/HTTPServer/conf/admin.passwd
Require user ihsadmin
```

When you create the web server definition in the WAS console, the wizard asks for:

- **User ID** → `ihsadmin`
- **Password** → (what you set)

DMGR stores these credentials and uses them every time it talks to port `8008`.

> [!TIP]
> **Analogy:** DMGR has a *key* to IHS's back door. It knocks on port 8008, shows the key, and gets in.

---

## 4. Managed IHS

**"Managed" = DMGR controls IHS directly.**

### How It Works

```
DMGR ──(port 8008, with username/password)──► IHS Admin Server
                                                     │
                                                     ▼
                                         Main IHS (port 80/443)
```

### What DMGR Can Do (all 1-click from console)

- ✅ **Propagate plugin** — push `plugin-cfg.xml` automatically
- ✅ **Start IHS**
- ✅ **Stop IHS**
- ✅ **Restart IHS**

### Setup Steps (Summary)

1. Install IHS on the web server machine.
2. Start the Admin Server on port `8008`.
3. Create the password file (`htpasswd`).
4. In WAS console, create the web server definition + enter credentials.
5. Done — DMGR now pushes everything automatically.

### Real-Life Example

A bank's production site in a normal data center:

1. Cluster gets a new app deployed.
2. Admin clicks **"Generate and Propagate Plugin."**
3. DMGR pushes the file to all IHS servers in seconds — no manual work.

> [!NOTE]
> This is why most large banks use **Managed** mode.

---

## 5. Unmanaged IHS

**"Unmanaged" = DMGR cannot touch IHS at all.**

### Why Would Anyone Want That? — Security

Think of a strict **DMZ** (the "no man's land" between the internet and your internal network).

Security policy says:

- ❌ No internal server may connect **INTO** the DMZ.
- ❌ No extra ports open on the DMZ server.
- ❌ DMGR → IHS connection is **forbidden** (firewall blocks it).

Therefore:

- The Admin Server is **not running** (maybe not even installed).
- No port `8008`.
- DMGR **can generate** the plugin file (on its own machine) — that's just local file creation.
- But DMGR **cannot deliver it**. A human must.

### How Plugin Delivery Works Manually

**Step 1** — Admin clicks **Generate Plugin** in WAS console. The file appears on the DMGR machine.

**Step 2** — Admin copies it by hand:

```bash
scp /opt/IBM/WebSphere/AppServer/profiles/Dmgr01/ \
    config/cells/citiCell/nodes/webserver1/ \
    servers/webserver1/plugin-cfg.xml \
    ihsadmin@10.10.1.50:/opt/IBM/WebSphere/Plugins/ \
    config/webserver1/plugin-cfg.xml
```

**Step 3** — Restart IHS **manually** so it picks up the new file.

### What You See in the WAS Console

- ❌ "Propagate Plugin" button → **greyed out**
- ❌ "Start/Stop IHS" buttons → **greyed out**

> [!NOTE]
> The web server definition still exists in the console — DMGR just *knows about it* but **can't control it**.

### Real-Life Example

A payment system under **PCI-DSS** rules (credit card data). Auditors demand the DMZ be fully isolated. **Unmanaged** mode is the standard answer.

---

## 6. The Analogy to Remember 🏠

### Managed IHS = House with a trusted housekeeper

- You (DMGR) have a key.
- Housekeeper (Admin Server) lets you in.
- You deliver mail (plugin), turn lights on/off (start/stop), **anytime**.

### Unmanaged IHS = House in a gated secure compound

- Guards (firewall) won't let anyone in.
- Mail is left at the gate (DMGR generates the file).
- You personally walk in and hand-deliver it (**manual SCP**).

---

## 7. Side-by-Side — Memorize This Table

| Feature | MANAGED | UNMANAGED |
|---|---|---|
| Admin Server on 8008 | ✅ Running | ❌ Not running |
| `admin.passwd` needed | ✅ Yes | ❌ No |
| DMGR → IHS connectivity | ✅ Required | ❌ Not needed |
| Propagate plugin (GUI) | ✅ 1 click | 🚫 Greyed out |
| Start/Stop from GUI | ✅ Yes | 🚫 No |
| Plugin delivery | DMGR pushes | Admin SCPs manually |
| Setup complexity | More steps | Fewer steps |
| Security exposure | Port 8008 open | No extra port |
| Typical use | Normal PROD | Strict DMZ / PCI-DSS |

---

## 8. Key Exam/Interview Points 💡

- `plugin-cfg.xml` is the **heart of everything** — IHS reads it to route traffic to WAS.
- **Managed** = Admin Server on `8008` + credentials stored in DMGR.
- **Unmanaged** = manual file copy; DMGR can **generate** but not **deliver**.
- **Greyed-out buttons** in the console = the #1 symptom you're looking at an unmanaged web server.
- `htpasswd` creates the credential file; the wizard in WAS console stores those same credentials.
- Unmanaged is chosen for **security, not convenience** — it's actually more work day-to-day.

---

## 9. One-Line Summary

> **Managed** = DMGR has a key to IHS's back door (port 8008).
> **Unmanaged** = No key exists — a human carries the plugin file by hand.

# IBM HTTP Server (IHS) — Managed vs Unmanaged in WebSphere Application Server

A practical guide to understanding, choosing, and operating IBM HTTP Server in **Managed** or **Unmanaged** mode within a WebSphere Application Server (WAS) cell.

---

## 1. Overview

IBM HTTP Server acts as the front-end web server (the "receptionist") that routes traffic to the WAS application cluster via the WebSphere plugin.

There are two operating modes:

- **Managed** — IHS is part of the WAS cell and controlled by the Deployment Manager (DMGR).
- **Unmanaged** — IHS is outside the cell and controlled manually by administrators.

> [!TIP]
> Memory hook: **Managed = convenience. Unmanaged = security.**

---

## 2. Side-by-Side Comparison

| Aspect | Managed | Unmanaged |
|---|---|---|
| Part of WAS cell? | Yes | No |
| Node Agent on IHS box? | Yes | No |
| Plugin file pushed by? | DMGR (automatic) | Human (manual SCP) |
| Admin Server needed? | Yes (port 8008) | Not required |
| Start/stop IHS from DMGR console? | Yes | No (must log in and run `apachectl`) |
| Speed of config sync | Instant | Depends on admin |
| Security footprint | Larger (mgmt port open) | Smaller (nothing listens for control) |
| Typical use | Dev, Test, UAT | Production DMZ, banks |

---

## 3. Why Choose Unmanaged? (The Senior Admin Question)

Managed sounds better — so why not always? **Answer: Security, specifically firewalls in a DMZ.**

### What Is a DMZ?

A **DMZ (Demilitarized Zone)** is a neutral network zone between the internet and the internal network:

```text
Internet
   │
[Firewall 1]        ← blocks bad internet traffic
   │
[IHS — in DMZ]      ← the receptionist sits in the lobby
   │
[Firewall 2]        ← blocks traffic between lobby and office
   │
[WAS Cluster + DMGR — internal]
```

### The Problem

- Normal traffic (users → app) flows from the DMZ into the internal network. Firewall 2 allows ports such as `80`, `443`, `9080`, `9443`.
- **Managed mode requires port `8008` traffic flowing the *other* way** — from internal (DMGR) into the DMZ (IHS).

### Security Team's Logic

> "If a hacker gets into the internal NOT be able to push files into the DMZ. A pushed file could be malware. So we block all inbound management ports into the DMZ."

That rule kills Managed mode. The bank therefore decides:

> "IHS in this DMZ will be Unmanaged. Admins copy plugin files manually during approved change windows."

It's slower — but safer. In banking, slower is acceptable; a breach is not.

---

## 4. Simple Decision Guide

### Choose **Managed** when:

- ✅ Dev/Test/UAT environments (speed over paranoia)
- ✅ IHS is on the same network as WAS (no DMZ)
- ✅ Cluster changes happen often
- ✅ Small ops team (automation saves labor)
- ✅ Security allows port `8008`

### Choose **Unmanaged** when:

- ❌ Strict PCI-DSS DMZ (no inbound management ports allowed)
- ❌ IHS is air-gapped (physically disconnected)
- ❌ Different security zones with tight firewall rules
- ❌ DR site with isolated IHS
- ❌ Auditors demand: *"Nothing external can push files to the DMZ" 5. The Admin Server — The Secret Manager Behind Managed Mode

Even in Unmanaged mode, IHS has an optional helper called the **Admin Server**.

- A second, small web server running alongside the main IHS.
- Only job: management tasks — receive plugin files from DMGR, allow remote start/stop of IHS.
- Controlled by `adminctl` (same style as `apachectl`).
- Listens on port `8008`.
- Login requires credentials in `admin.passwd` (created with `htpasswd`).

> [!NOTE]
> Think of it like this:
> - `httpd` = the receptionist serving customers (real traffic, ports 80/443)
> - Admin Server = the receptionist's back-office line for the boss (port 8008)

If Managed mode is disabled or security forbids it, simply don't run the Admin Server.

---

## 6. Complete File, Process, and Port Map

### Binaries (programs you run)

| Path | Purpose |
|---|---|
| `/opt/IBM/HTTPServer/bin/httpd` | Main web server program |
| `/opt/IBM/HTTPServer/bin/apachectl` | Start/stop/restart the main web server |
| `/opt/IBM/HTTPServer/bin/adminctl` | Start/stop the Admin Server |
| `/opt/IBM/HTTPServer/bin/htpasswd` | Create the Admin Server password file |

### Config files (settings)

| Path | Purpose |
|---|---|
| `/opt/IBM/HTTPServer/conf/httpd.conf` | Main IHS configuration (ports, virtual hosts, plugin file location) |
| `/opt/IBM/HTTPServer/conf/admin.conf` | Admin Server configuration |
| `/opt/IBM/HTTPServer/conf/admin.passwd` | Admin Server usernames/passwords |

### Log files (what happened)

| Path | Purpose |
|---|---|
| `logs/error_log` | Main IHS errors — **your first stop when troubleshooting** |
| `logs/access_log` | Every request IHS served |
| `logs/admin_error_log` | Admin Server errors |
| `logs/admin_access_log` | Admin Server activity (e.g., DMGR pushing a plugin file) |

### Ports

| Port | Purpose |
|---|---|
| `80` | HTTP traffic (customers) |
| `443` | HTTPS traffic (customers, encrypted) |
| `8008` | Admin Server (management, DMGR → IHS) |

### Processes (what you see in `ps`)

- Multiple `httpd` processes → one parent + several workers serving traffic
- Separate `httpd` (admin) workers → the Admin Server, if running

---

## 7. Quick Memory Cards

### Card 1 — The Core Idea
- Managed = DMGR pushes plugin file automatically.
- Unmanaged = you copy the plugin file manually.

### Card 2 — The Port
- `8008` = Admin Server = the door DMGR uses to reach IHS.
- No `8008` open = no Managed mode.

### Card 3 — The Decision
- Convenience + same network → Managed.
- DMZ + strict security → Unmanaged.

### Card 4 — The DMZ Logic
- Traffic DMZ → Internal for users = allowed.
- Traffic Internal → DMZ for management = usually forbidden.
- That's why real banks often run Unmanaged IHS.

---

## 8. Real-World Admin Workflows

### On a Managed IHS

1. Change cluster in the DMGR console.
2. Click **Generate Plugin** and **Propagate Plugin**.
3. Done — IHS has the new file.

### On an Unmanaged IHS

```bash
# 1. Change cluster in the DMGR console.
# 2. Generate plugin on the DMGR side.
# 3. SCP the file to the IHS box (during an approved change window).
scp plugin-cfg.xml admin@ihs-host:/opt/IBM/HTTPServer/Plugins/config/webserver1/

# 4. Gracefully reload IHS.
/opt/IBM/HTTPServer/bin/apachectl graceful

# 5. Verify.
tail -f /opt/IBM/HTTPServer/logs/error_log
curl -I https://your-app-url/
```

> [!TIP]
> Always validate routing after a plugin change by testing a real URL and watching `error_log` for plugin load messages.

---

## Summary

> **Managed means the boss updates the receptionist remotely through port 8008. Unmanaged means no boss line exists, so a human walks the update over — slower, but the DMZ stays sealed.**

# IBM HTTP Server (IHS) — Determining Managed vs. Unmanaged Status in WebSphere Admin Console

## Overview

This document explains how to determine whether an **IBM HTTP Server (IHS)** instance is **managed** or **unmanaged** from the **WebSphere Application Server (WAS) Administrative Console**, and how to interpret the **Status** column for the IHS web server definition.

> [!NOTE]
> Knowing whether IHS is managed or unmanaged is critical before attempting plugin propagation, server start/stop operations, or admin server troubleshooting from the console.

---

## 1. Path to Check Managed vs. Unmanaged Status

Navigate through the WebSphere Administrative Console:

```text
Servers → Server Types → Web Servers → [click webserver1]
```

Once inside the web server definition, inspect the **Properties** tab.

---

## 2. Managed vs. Unmanaged — Key Indicators

Compare the fields on the **Properties** tab:

| Field                          | Managed IHS            | Unmanaged IHS        |
|--------------------------------|------------------------|----------------------|
| **Administration port**        | `8008`                 | *(blank or N/A)*     |
| **Use administrative agent**   | ✅ Checked              | ❌ Unchecked          |
| **"Propagate Plugin" button**  | Active                 | Greyed out           |
| **"Start" / "Stop" buttons**   | Active                 | Greyed out           |

> [!TIP]
> The **"Propagate Plugin"** button state is the **fastest visual indicator** of whether your IHS is managed. If it is greyed out, the IHS is unmanaged (or the admin connection is broken).

### Indicator Breakdown

- **Administration port (`8008`)** — Present only when the IHS Admin Server is configured. Unmanaged IHS instances have no admin port defined.
- **"Use administrative agent" checkbox** — When checked, the WAS console can communicate with the IHS Admin Server for remote operations.
- **"Propagate Plugin" button** — Requires an active admin connection to the IHS Admin Server. Greyed out = no admin connection = unmanaged.
- **"Start" / "Stop" buttons** — Only functional when the console can reach the IHS Admin Server.

---

## 3. How to Check Admin Server Status from the Console

Navigate to:

```text
Servers → Server Types → Web Servers → [Select webserver1]
```

Check the **Status** column:

| Status Icon  | Meaning                                              |
|--------------|------------------------------------------------------|
| 🟢 **Started** | IHS main process is up and running.                  |
| 🔴 **Stopped** | IHS main process is down.                            |
| ❓ **Unknown** | Admin Server is **not reachable** — this is the Unmanaged state, or the Admin Server itself is down. |

> [!NOTE]
> A status of **Unknown** does not necessarily mean IHS is not serving traffic. It only means the console cannot verify the process state because the **IHS Admin Server** is unreachable or not configured.

---

## 4. Quick Troubleshooting Checklist

If the status shows **Unknown** or buttons are greyed out:

- [ ] Verify the IHS **Admin Server** is running on the IHS host:
 ```bash
 ps -ef | grep adminctl   # Linux/Unix
 ```
- [ ] Start the Admin Server if stopped:
 ```bash
 <IHS_HOME>/bin/adminctl start
 ```
- [ ] Confirm the **administration port** (default `8008`) is open:
 ```bash
 netstat -an | grep 8008
 ```
- [ ] Verify **firewall rules** allow WAS (Node Agent / Deployment Manager) → IHS Admin port traffic.
- [ ] Confirm the web server definition in the WAS console has the correct **host name** and **admin port** values.
- [ ] Check `httpd.conf` / `admin.conf` for the `Listen 8008` directive under the Admin Server configuration.

> [!TIP]
> To make an unmanaged IHS manageable, configure the **IHS Administration Server** on the web server host and re-federate/redefine the web server in the WAS console with the admin port and administrative agent option enabled.

---

## 5. Summary

| Scenario                  | Console Behavior                                  | Action Required                     |
|---------------------------|---------------------------------------------------|-------------------------------------|
| Managed + Admin up        | 🟢 Started, buttons active                        | None                                |
| Managed + Admin down      | ❓ Unknown or buttons inactive                    | Start `adminctl` on IHS host        |
| Unmanaged                 | ❓ Unknown, "Propagate Plugin" greyed out         | Configure Admin Server or manage IHS manually |

**Key takeaway:** Use the **"Propagate Plugin"** button state as your fastest check, and the **Status column** to verify Admin Server reachability.
