# PART 9 — Plugin Generate & Propagate (Explained Simply)

---

## 1. The Real-Life Picture First

Think of a bank branch:

- **IHS** = The reception desk. Customers walk in here first.
- **WebSphere (WAS)** = real work happens.
- **plugin-cfg.xml** = A piece of paper on the reception desk that says:

> *"If a customer asks for X, send them to this back-office desk. There are 3 back-office desks — try one, if busy try the next."*

Without that paper, the receptionist doesn't know where to send customers. That's it. That's the whole concept.

---

## 2. What is plugin-cfg.xml?

One file. Generated by WebSphere. It contains:

- **Server list** — where the WAS servers live (IP + port)
- **URL rules** — which URLs go to which cluster (e.g., `/digibank/*` → `DigiBankCluster`)
- **Load balancing** — round robin, retries, timeouts

**Who reads it?** Only IHS. WAS doesn't need it. It's purely for IHS to know how to forward requests.

---

## 3. The Flow (Memorize This)

```text
DigiBank.ear deployed to DigiBankCluster
        |
        v
WebSphere generates plugin-cfg.xml  <-- Step 1: GENERATE
        |
        v
File sits on the DMGR (stays there)
        |
        v
Copy it to the IHS server          <-- Step 2: PROPAGATE
        |
        v
IHS now routes requests to WAS
```

**Key point:** Generate = create the file. Propagate = copy it to IHS. **Two separate actions.** Newbies always forget the second one.

---

## 4. Why Propagate Again and Again?

Every time something changes, the paper on the reception desk is outdated:

- You deploy a **new application**
- You **add/remove a server** from the cluster
- You **change URL mappings**

Old plugin = IHS sends requests to wrong/dead places = errors for users.

> **Banking reality:** Plugin refresh is part of every deployment checklist. No plugin refresh = the app may not be reachable even though it deployed fine.

---

## 5. Generate Plugin — Admin Console

Path:

```text
Servers -> Server Types -> Web Servers -> webserver1 -> Generate Plug-in
```

Success message:

```text
PLGC0062I: The plug-in configuration file was successfully written.
```

That message = file created. Note it down for your runbook.

---

## 6. Generate Plugin — wsadmin

```python
# Get the web server object
webServer = AdminConfig.getid('/WebServer:webserver1/')

# Generate the plugin
AdminControl.invoke(webServer, 'generatePlugin', '', '')

AdminConfig.save()
```

Or with AdminTask (cleaner):

```python
AdminTask.generatePluginCfg(['-webServerName', 'webserver1',
                             '-nodeName', 'Node01'])
AdminConfig.save()
```

> **Don't forget** `AdminConfig.save()`. No save = nothing happened.

---

## 7. Propagate Plugin — Admin Console

Same path:

```text
Servers -> Server Types -> Web Servers -> webserver1 -> Propagate Plug-in
```

This copies the file to the IHS server at:

```text
/opt/IBM/WebSphere/Plugins/config/webserver1/plugin-cfg.xml
```

That exact path matters. If IHS is looking at a different path, it won't work.

---

## 8. Propagate Plugin — wsadmin

```python
AdminControl.invoke(webServer, 'propagatePlugin', '', '')
AdminConfig.save()
```

---

## 9. Manual Propagation (When It Fails)

**Why it fails in real life:** The DMGR needs to SSH/FTP to the IHS server to copy the file. In banks, firewalls often block this. Very common.

### Step 1 — Find the file on the DMGR

```bash
find /opt/IBM/WebSphere/AppServer -name "plugin-cfg.xml" \
  -path "*webserver1*"
```

### Step 2 — Copy it to the IHS server

```bash
scp /opt/IBM/WebSphere/AppServer/profiles/Dmgr01/config/cells/\
DigiBank_Cell/nodes/Node01/servers/webserver1/plugin-cfg.xml \
ibmhttpd@ihs01:/opt/IBM/WebSphere/Plugins/config/webserver1/plugin-cfg.xml
```

### Step 3 — Fix ownership and permissions (important!)

```bash
chown ibmhttpd:ibmhttpd \
  /opt/IBM/WebSphere/Plugins/config/webserver1/plugin-cfg.xml
chmod 644 \
  /opt/IBM/WebSphere/Plugins/config/webserver1/plugin-cfg.xml
```

**Why step 3?** IHS runs as user `ibmhttpd`. If the file is owned by root or unreadable, IHS can't read it → routing fails.

---

## 10. After Propagating — Restart or Reload IHS

IHS may not pick up the new plugin immediately. Either:

- Restart IHS:

  ```bash
  /opt/IBM/HTTPServer/bin/apachectl restart
  ```

- Or wait — IHS periodically re-reads the file (default refresh interval is **60 seconds**)

---

## 11. Quick Verification Checklist

- [ ] File exists on IHS:

  ```bash
  ls -l /opt/IBM/WebSphere/Plugins/config/webserver1/plugin-cfg.xml
  ```

- [ ] File contains your cluster and server names:

  ```bash
  grep -i digibank plugin-cfg.xml
  ```

- [ ] Permissions: readable by `ibmhttpd`
- [ ] IHS restarted or 60s passed
- [ ] Test: hit the app URL through IHS port (e.g., `http://ihs01:80/digibank`)

---

## 12. Summary — 5 Things to Remember

1. **plugin-cfg.xml** = IHS's instruction sheet for routing to WAS.
2. **Generate** = create/update the file. **Propagate** = copy it to IHS. Always both.
3. Regenerate + propagate after **every deployment or topology change**.
4. If automatic propagation fails (firewall), do it **manually with scp** and fix permissions.
5. If the site is down after a deployment — **check the plugin first**. It's the #1 culprit.
