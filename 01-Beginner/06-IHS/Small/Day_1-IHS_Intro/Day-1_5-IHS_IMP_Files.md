# IBM HTTP Server (IHS) IMP Files

## 🏦 The Bank Branch Analogy

Imagine a bank branch.

- **Customer** walks in (browser request).
- **Security guard at the door** = **IHS (web server)**.
- **Guard's instruction sheet** = **httpd.conf**.
- **Guard asks:** "Which counter should I send this customer to?" → He checks a **phone directory** = **plugin-cfg.xml**.
- **Bank tellers** = **WAS servers (WebSphere)**.
- **CCTV register of visitors** = **access_log**.
- **Incident book** = **error_log**.
- **Guard's diary of who he sent where** = **http_plugin.log**.

---

## 1. httpd.conf — The Guard's Rule Book

**Location:** `/opt/IBM/HTTPServer/conf/httpd.conf`

This is the **main configuration file of IHS**. The web server reads it every time it starts.

### What's inside:

- **Port to listen on** — usually port `80` (HTTP) or `443` (HTTPS).
- **Document root** — where static files (HTML, images) live.
- **Log file locations** — where `access_log` and `error_log` are.
- **Plugin module load** — a line like:

  ```apache
  LoadModule was_ap22_module modules/mod_was_ap22.so
  ```

  This loads the WAS plugin into IHS.
- **Plugin config reference:**

  ```apache
  WebSpherePluginConfig /opt/IBM/HTTPServer/Plugins/config/webserver1/plugin-cfg.xml
  ```

### Real-life points:

- Change anything here → **restart IHS** for it to take effect.
- Wrong syntax here → IHS **won't start at all**.

> 💡 **Admin tip:** Always take a backup before editing:

```bash
cp httpd.conf httpd.conf.backup_$(date)
```

---

## 2. plugin-cfg.xml — The Phone Directory

**Location:** `/opt/IBM/HTTPServer/Plugins/config/webserver1/plugin-cfg.xml`

This is the **most important file for routing**. It tells the plugin:

> *"Which WAS servers exist, on which host, which port, and which URLs to send them."*

### What's inside:

- **Server list** — WAS hostnames and ports (e.g., `myhost:9080`).
- **Cluster info** — if you have multiple WAS servers, it lists all of them (for load balancing).
- **URI groups** — which URLs go to WAS (e.g., `/bankapp/*`).
- **Routes** — URL → server mapping.

### How it gets generated/updated:

- Generated by **WebSphere** (via `genplugin` / Deployment Manager).
- Copied or **propagated** to the IHS plugin directory.
- Plugin **re-reads it periodically** (default every 60 seconds) — usually **no IHS restart needed**.

### Real-life example:

- Customer opens `www.mybank.com/banking/login`.
- IHS sees `/banking/*` in `plugin-cfg.xml` → forwards to WAS at `serverA:9080`.
- If WAS is **down**, plugin tries **serverB** (failover).

### Common problems:

- **Stale plugin-cfg.xml** → requests go to dead server → `404` / `503`.
- **Fix:** regenerate + propagate plugin, then check.

---

## 3. access_log — Visitor Register

**Location:** `/opt/IBM/HTTPServer/logs/access_log`

Records **every single request** that reaches IHS.

### Sample line:

```
10.20.30.40 - - [10/Jun/2025:10:15:32] "GET /banking/login HTTP/1.1" 200 5123
```

### How to read it:

| Field | Meaning |
|---|---|
| `10.20.30.40` | Client IP |
| `GET /banking/login` | What they asked for |
| `200` | Status code (success) |
| `5123` | Size of response in bytes |

### Why admins love it:

- Traffic volume check (how many users at 10 AM?).
- Find **who hit which URL**.
- Spot **4xx and 5xx errors** quickly.

### Useful commands:

```bash
grep " 500 " access_log          # find server errors
tail -f access_log               # live traffic watch
awk '{print $1}' access_log | sort | uniq -c | sort -rn   # top IPs
```

---

## 4. error_log — The Incident Book

**Location:** `/opt/IBM/HTTPServer/logs/error_log`

Records **IHS problems**, not normal requests.

### Typical contents:

- IHS start/stop messages.
- Startup failures (e.g., "Address already in use" → port 80 taken).
- Configuration errors (bad line in httpd.conf).
- Plugin load failures.

### Real-life example:

IHS won't start → open `error_log` →

```
(98)Address already in use: make_sock: could not bind to port 80
```

**Meaning:** Another process owns port 80. Kill it or change the port.

> 💡 **Admin tip:** `error_log` is your **FIRST stop** when IHS misbehaves.

---

## 5. http_plugin.log — The Guard's Diary

**Location:** `/opt/IBM/HTTPServer/Plugins/logs/webserver1/http_plugin.log`

Records what the **plugin** did — how it routed each request.

### Typical contents:

- Which WAS server the request went to.
- Why a server was rejected (down, busy).
- Plugin config load times.
- Routing failures.

### Real-life example:

- User gets **503 Service Unavailable**.
- You check `http_plugin.log` →

  ```
  ERROR: ws_server: serverMarkServerStatus failed
  All endpoints for server serverA are marked down
  ```

- **Meaning:** Plugin thinks all WAS servers are dead → check **WAS**, not IHS.

> 💡 **Admin tip:** `404` in access_log + plugin log shows routing attempt → check **URI group** in `plugin-cfg.xml`.

---

## 📌 Quick Memory Table

| Situation | Which file to check? |
|---|---|
| IHS won't start | `error_log` |
| "Did my request arrive?" | `access_log` |
| "Where did my request go?" | `http_plugin.log` |
| "Which WAS servers are configured?" | `plugin-cfg.xml` |
| "Which port is IHS listening on?" | `httpd.conf` |

---

## 🔁 Classic Troubleshooting Flow (memorize this)

1. User reports error.
2. Check **access_log** → did the request reach IHS?
   - **Not there** → network/firewall/DNS problem.
3. Check **http_plugin.log** → did plugin route it?
   - Plugin says server down → check **WAS**.
4. Check **error_log** → any IHS-level issue?
5. Verify **plugin-cfg.xml** has correct servers/ports.

---

## ✅ Key Takeaways (One-Liners)

- **httpd.conf** = how IHS behaves.
- **plugin-cfg.xml** = how requests reach WAS.
- **access_log** = every request.
- **error_log** = IHS problems.
- **http_plugin.log** = routing decisions.
- Backup config files before editing.
- Plugin config changes → usually **no restart**; httpd.conf changes → **restart IHS**.

# IMP Log Files

## 1. access_log — "Who came and asked for what?"

**Every request IHS receives is recorded here.**

**Example line:**

```
192.168.1.1 - - [29/Aug/2026:10:15:01 +0000] "GET /internetbanking/login HTTP/1.1" 200 4523
```

**Reading this line piece by piece:**

| Piece | Meaning |
|---|---|
| `192.168.1.1` | Customer's IP address |
| `[29/Aug/2026:10:15:01 +0000]` | Date and time of request |
| `GET` | Type of request (GET = view, POST = submit data) |
| `/internetbanking/login` | What they requested |
| `HTTP/1.1` | Protocol version |
| `200` | Status code → **success** |
| `4523` | Response size in bytes |

**Status code cheat sheet:**

| Code | Meaning |
|---|---|
| `200` | OK ✅ |
| `404` | Page not found ❌ |
| `403` | Forbidden (no permission) 🚫 |
| `500` | Application error 💥 |
| `503` | Service unavailable (often: WAS down) ⛔ |

---

## 2. error_log — "What went wrong?"

**Records problems, warnings, and IHS startup/shutdown messages.**

**Example line:**

```
[Mon Aug 29 10:15:01 2026] [error] [client 192.168.1.1] File does not exist: /opt/IBM/HTTPServer/htdocs/favicon.ico
```

**Reading this line:**

| Piece | Meaning |
|---|---|
| `[Mon Aug 29 10:15:01 2026]` | When it happened |
| `[error]` | Severity level (error, warn, notice) |
| `[client 192.168.1.1]` | Which customer triggered it |
| `File does not exist: ...favicon.ico` | The actual problem |

**Severity levels (top = worst):**

- `emerg` — IHS is dying
- `alert`, `crit` — serious
- `error` — something failed
- `warn` — caution
- `notice`, `info` — normal messages

> 💡 `File does not exist` for `favicon.ico` = **harmless, ignore it**.

---

## 3. http_plugin.log — "Where did I send the customer?"

**Records plugin decisions — which WAS server got the request, connection errors, failover events.**

**Example line:**

```
[Mon Aug 29 10:15:01 2026] 00000023 00012345 - ERROR: ws_common: websphereExecute: Failed to connect to app server
```

**Reading this line:**

| Piece | Meaning |
|---|---|
| `[Mon Aug 29 10:15:01 2026]` | When |
| `00000023 00012345` | Internal thread/process IDs (ignore) |
| `ERROR:` | Severity |
| `Failed to connect to app server` | Plugin could NOT reach a WAS server |

**Real-life use:**

- User gets **503** → this line in plugin log → **check WAS, not IHS**.

---

## 🔍 Golden Rule: Follow the Request

```
1. access_log      → Did the request reach IHS?        (No → network/DNS issue)
2. http_plugin.log → Did the plugin route it to WAS?   (Failed → WAS issue)
3. error_log       → Any IHS-level problem?            (Yes → fix IHS config)
4. WAS logs        → Did WAS handle it?                (check SystemOut.log)
```

**Wherever the trail stops — that's where the problem is.** 🎯

---

## ✅ Key Takeaways

- **access_log** = requests + status codes.
- **error_log** = IHS problems with severity levels.
- **http_plugin.log** = routing + connection failures to WAS.
- `503` + "Failed to connect" in plugin log = **check WAS**.
- Follow the request through logs in order — **where the trail stops is the problem**.
